Section 03 · Making It Train

The released code cannot train

Chapter 14 of 30 ⏱ 11 min read 📊 5 figures 4 bugs

An assert against training mode, a NotImplementedError in the MoE forward, a balancer bias that is never initialised, and a timestep bias left as uninitialised memory that returned NaN on one rung and trained fine on another.

Moonshot released Kimi K3 with working modeling code. It loads the checkpoint, it runs a forward pass, it generates text, and every part of it is correct for the thing it was written to do. It cannot train, and it cannot train for four separate reasons, none of which is documented anywhere in the repository.

We found all four in one afternoon, before a training loop existed, by running a GPU smoke test: build each rung of the ladder from scratch, take two optimizer steps on a short sequence, and assert that the loss is finite, starts near ln(163,840) = 12.007 and goes down. That is a small amount of work to arrange, and it is the reason this chapter is about four bugs rather than about a run that died at hour nine.

The four have a common cause, and it is worth naming before the details. Released inference code is code that has only ever been exercised in one mode, by one caller, with every tensor loaded from a checkpoint. Anything that matters only in the other mode was never wrong in a way anyone would notice.

Blocker one: the router asserts it is not training

KimiMoEGate.forward computes its logits, applies the sigmoid, and then, immediately before top-k selection, does this:

# select top-k experts
assert not self.training

That is the whole blocker. Calling model.train() and running a forward pass raises AssertionError with no message. It is the friendliest of the four, because it fails on the first forward, in the first second, with a stack trace pointing at the exact line.

Why the assert is there is not stated, and we did not ask. The reasonable reading is that the gate's training path was never written, so the author blocked the door rather than leaving a silently-wrong path open. Our replacement, TrainableMoEGate in train/moe_train.py, copies the selection arithmetic from the reference line for line so that inference behaviour is unchanged, and adds the training path: load statistics, entropy, and the balancer state.

Blocker two: there is no differentiable dispatch

The second blocker sits one level up, in the sparse block that owns the experts:

if not self.training:
    y = self.moe_infer(hidden_states, topk_idx, topk_weight)
else:
    raise NotImplementedError("Training mode is not supported in KimiSparseMoeBlock")

moe_infer is the only dispatch in the file, and it is decorated @torch.no_grad(). Removing the NotImplementedError and calling it anyway would not help: nothing inside it carries a gradient, so the experts would produce outputs and receive none of the loss.

Dispatch is the operation that takes a batch of tokens, each routed to six of 256 experts, and arranges them so each expert can process its own tokens as one contiguous matrix. The reference does it by sorting the flattened expert indices, gathering the tokens into that order, running each expert on its slice, and then writing the results back with an in-place index assignment into a torch.empty_like buffer.

The rewrite keeps the same arithmetic and changes two things. Nothing runs under no_grad, and the scatter back is done with an inverse permutation and a gather rather than an in-place write into uninitialised memory:

n_tok, k = topk_idx.shape
flat = topk_idx.reshape(-1)
order = flat.argsort()
sorted_tokens = hidden_states[order // k]        # differentiable gather
counts = torch.bincount(flat, minlength=len(self.experts))

chunks = []
start = 0
for i, c in enumerate(counts.tolist()):
    if c == 0:
        continue
    chunks.append(self.experts[i](sorted_tokens[start:start + c]))
    start += c
outs = torch.cat(chunks, dim=0)

inv = torch.empty_like(order)
inv[order] = torch.arange(order.numel(), device=order.device)
y = outs[inv]                                     # undo the sort, by gather

An index assignment into a fresh empty tensor is a poor autograd citizen: the buffer starts as garbage, the write is in place, and the gradient has to be threaded back through an operation whose output partly does not come from any input. A gather has none of those properties and is exactly as fast.

That Python expert loop is the version we started with, and it is also the single largest throughput problem in the project. Replacing it with a batched dispatch was worth 17.5x, taking MFU from 0.1% to 4.1% — measured on r2, the rung above ours, since that is where the MFU work was done. It has its own chapter in Making It Fast. For now the loop is correct, which is what the smoke test needed it to be.

Blocker three: the balancer does not exist

K3's config names its load-balancing method in one field, topk_method: noaux_tc, and the released gate declares the tensor that method writes to:

self.e_score_correction_bias = nn.Parameter(
    torch.empty(self.num_experts),
)
self.reset_parameters()

reset_parameters initialises self.weight and stops. The bias is left as torch.empty, and nothing in the file ever adds anything to it.

For inference this is complete. from_pretrained overwrites every parameter with a loaded tensor, so the bias arrives fully formed, holding whatever values Moonshot's own training produced.1 This is the mechanism behind three of the four blockers. A parameter that is always overwritten by loaded weights can be left uninitialised with no observable consequence, and a module's _init_weights can cover only the layer types the author happened to think about, because in the checkpoint-loading path it does not run on anything that matters. For pretraining from scratch, the tensor holds uninitialised memory on step 0 and never changes afterwards, which means routing is decided partly by whatever was in that page for the entire run.

So the balancer had to be written. The rule is one line, inherited by K3 from DeepSeek-V3:

bias_i += gamma * sign(mean_load - load_i)

Our implementation declares the bias with torch.zeros, sets requires_grad_(False), and holds it out of AdamW's parameter groups. It is updated by rule, not by gradient, and letting the optimizer see it would apply weight decay and momentum to a quantity whose update is already fully specified. The two rules would then disagree about where the bias should be.

Choosing gamma is a measurement rather than a default, and it is the subject of the chapter on expert collapse, where the value inherited from DeepSeek-V3 turns out to be wrong for our batch size by a factor of ten. The point here is narrower: without this code, noaux_tc is a string in a config file.

Blocker four: a bias that is whatever was in that allocation

The fourth is the one worth spending time on, because it is the only one that does not announce itself.

KimiDeltaAttention builds two raw parameters by hand. One of them is initialised in place:

self.A_log = torch.nn.Parameter(torch.log(torch.empty(
    self.num_heads, dtype=torch.float32).uniform_(1, 16)))

...

self.dt_bias = nn.Parameter(
    torch.empty(projection_size, dtype=torch.float32))

A_log calls .uniform_(1, 16) on its empty tensor and is fine. dt_bias, eleven lines later in the same constructor, does not. And KimiPreTrainedModel._init_weights, which is the mechanism that would ordinarily catch it, handles nn.Linear and nn.Embedding and nothing else. A bare nn.Parameter is neither.

dt_bias is the timestep bias handed to the gated delta-rule kernel, one of nine KDA layers in r1. It is not a decorative term. It sits inside a softplus and sets the effective step size of the recurrence, so its magnitude controls how fast the linear-attention state decays.

Now consider what torch.empty actually returns. It allocates memory and does not write to it, so the tensor contains whatever bytes were already at that address, reinterpreted as float32. What those bytes are depends on the allocator, on what the process did earlier, on the CUDA caching allocator's block reuse, and on nothing you control. There are three ways this can go, and we saw two of them in the same smoke test:

  • The bytes decode to inf or NaN, or to values large enough that the kernel overflows. The loss is NaN on step 0 and the run is obviously broken.
  • The bytes decode to finite but wrong values. The model trains, the loss falls, every dashboard is green, and the recurrence has a step size nobody chose. There is no error and no alarm.
  • The bytes happen to be small and roughly sane. Nothing observable is wrong.

Rung r2 trained normally while r1 returned NaN from step 0, from the same code, in the same smoke run. The two models differ only in width and depth, so they allocate different-sized tensors in a different order, and their dt_bias allocations landed on different garbage. Had the ladder been r2-only, this bug would have shipped into the run.

The middle outcome is the reason this bug deserves a chapter section rather than a line in a changelog. A crash is a bug report. A silent quality regression is a model that is a little worse than it should be for a reason that will never be found, because there is nothing to search for. We would have spent the money, gotten a slightly worse loss curve, and attributed it to scale.

The fix, and the check that is not a fix

train/init_patch.py initialises dt_bias the way Mamba and GatedDeltaNet initialise their timestep parameters: sample a timestep uniformly in log-space over [1e-3, 1e-1], then invert the softplus so that softplus(dt_bias) covers that range.

dt = torch.exp(
    torch.rand(p.shape, device=p.device, dtype=torch.float32)
    * (torch.log(torch.tensor(dt_max)) - torch.log(torch.tensor(dt_min)))
    + torch.log(torch.tensor(dt_min))
).clamp(min=floor)
# inverse softplus: b = dt + log(-expm1(-dt))
p.copy_((dt + torch.log(-torch.expm1(-dt))).to(p.dtype))

Log-space rather than linear space, because the quantity being sampled spans two orders of magnitude and a linear sample would put almost all of the mass at the fast end. The inverse softplus is there because the kernel applies softplus to this parameter, so what we want to control is the distribution after that transform, not before it.

The second half of the file is not a fix. It is a check that runs before step 0:

def assert_initialised(model) -> dict:
    bad = []
    for name, t in list(model.named_parameters()) + list(model.named_buffers()):
        if t.is_floating_point() and not torch.isfinite(t).all():
            bad.append(name)
    if bad:
        raise ValueError(f"non-finite values in a freshly initialised model: {bad[:10]}")

Every parameter and buffer must be finite before the first forward pass. It costs one pass over the parameters, and it converts "the loss is NaN somewhere" into "this named tensor is bad", which is a different quality of debugging problem.

It is also incomplete, and the docstring in the file says so. Uninitialised memory is usually finite garbage rather than inf, so this check catches the loud outcome and misses the quiet one. It exists because the next uninitialised tensor will not announce itself either, and a cheap check that catches one case in three is worth having when the cost of the miss is a run that finishes and is wrong.2 The obvious stronger check is to compare every parameter's statistics against what the initialisation scheme should have produced, which would catch finite garbage as well. We did not build it. assert_initialised has caught nothing since init_dt_bias was written, which is the correct outcome for a guard and also the reason it is difficult to justify extending.

Two more traps in the same family

Neither of the next two is in the modeling code's arithmetic, and both belong to the same class: something that works in the released setting and quietly does not in ours.

transformers must be pinned to 4.57.6. The Kimi modeling code imports OutputRecorder at module scope. Version 5.x of transformers removed it, and a requirement of transformers>=4.56 resolves to 5.x, so the import fails before any model is constructed. A module-scope import error is at least a fast failure, but it is the kind of failure that appears weeks later on a fresh container image while the original environment continues to work, and it is worth a pin rather than a range.

gradient_checkpointing_enable() is a silent no-op on this modeling code. The model declares supports_gradient_checkpointing = True. KimiModel.__init__ sets self.gradient_checkpointing = False. The decoder loop then calls decoder_layer(...) directly, and there is no _gradient_checkpointing_func anywhere in the file. The flag is written and never read. KimiDecoderLayer is a plain nn.Module rather than transformers' GradientCheckpointingLayer, which is the only generic mechanism in the pinned version, so nothing else picks it up either.

Calling it produces the log line "use_cache=True is incompatible with gradient checkpointing", which is precisely the reassuring message you would expect if it were working.

The tell was in our own benchmark data and went unread for days. At 8,192 tokens per microbatch, peak memory read 76.7 GB with checkpointing off and 76.8 GB with it on. Activation checkpointing that is running trades memory for recomputation; it cannot leave memory unchanged. Identical memory is the signature of a no-op. The conclusion originally drawn from that grid, that checkpointing was slower per token but bought a larger microbatch and therefore won, compared two runs that differed only in batch size.

Real checkpointing needed one non-obvious thing beyond wrapping the layers: cfg.use_cache = False. The KV cache is mutated inside the forward pass, so the recomputed forward sees different state than the original and torch.utils.checkpoint raises CheckpointError. Setting use_cache=False was the one thing the no-op call had actually been doing.3 A related shim belongs to the same family and is described in the MFU chapters: MLA runs on an sdpa implementation registered under the flash_attention_2 key, because the model hard-forces that string and the asymmetric-head-dim padding only runs on that branch. It is numerically identical and slower, which means every MFU figure in this book understates what flash attention would give.

What the smoke test bought

All four blockers were found by smoke_all: build every rung, two steps, assert the loss is finite, starts near 12.007 and decreases. It takes a few minutes of GPU time and it was written before the training loop.

Three of the four would have been found anyway, in the first second of the first run, by a crash. The fourth would not. On r2 it does not crash, and on r1 it crashes only sometimes, so a project that smoke-tested one rung on one day had a real chance of carrying an uninitialised timestep bias into a multi-day run. What the smoke test bought was not the discovery of the loud bugs; it was running the same code on three models on the same afternoon, which is what made the non-deterministic one visible as non-determinism rather than as a mystery.4 The build path was later hardened for the same reason. train/build.py is now the only way any model is constructed, and it raises if a patch matched zero modules rather than proceeding. A patch that silently matched nothing produces a run that carries more memory than it should and gives up the fused kernel's 1.38x, with no error, which is the same failure shape as everything in this chapter.

The general form of the rule is this. Code released for inference has been exercised in one mode with every tensor loaded from disk. Before training with it, check the assumptions that only the other mode makes: which parameters are constructed rather than loaded, which branches are gated on self.training, which decorators suppress gradients, and which flags are written without being read. Every one of the four blockers, and both of the traps after them, is on that list.

The next chapter builds the training loop around this patched model: the WSD schedule, 131,072 tokens per step, and a spike protocol written down before the run rather than during it.
