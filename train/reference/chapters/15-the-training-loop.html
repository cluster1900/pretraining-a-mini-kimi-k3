Section 03 · Making It Train

The training loop

Chapter 15 of 30 ⏱ 14 min read 📊 7 figures WSD

Warmup, stable and decay instead of cosine; 131,072 tokens per step from 4,096 x 4 x 8; a learning rate transferred from one measured sweep; and the spike protocol written down before the run rather than at 3am.

A pretraining run is one loop body executed a very large number of times. Ours executed it 38,147 times over roughly 55 hours on a single H200, and every iteration did the same six things: read a batch, compute a loss, decide whether to trust that loss, take an optimizer step, nudge the router's balancing biases, and occasionally tell someone outside the process what happened.

The interesting design decisions are all in the fourth and sixth of those. This chapter is about the schedule that set the learning rate, the batch arithmetic that fed the loop, the protocol that decided when a step was not to be trusted, and the telemetry contract that made the run observable from outside. The chapter before this one covered the four blockers that had to be fixed before any of this could run at all. The chapter after it covers the router balancer whose update lives inside step five.

Warmup, stable, decay

The learning rate schedule almost every tutorial reaches for is cosine decay: start low, warm up, then follow a cosine curve down to some floor at the end of training. It works well and it has one property that is easy to overlook. Cosine commits you to a total step count on step one. The value of the cosine at step n depends on the total, so if you decide at step 20,000 that the run deserves another two billion tokens, you cannot simply continue. The schedule you have been following was shaped for a different endpoint, and extending it means the learning rate you have already applied was wrong for the run you are now doing.

We used WSD — warmup, stable, decay — instead. The learning rate ramps linearly over the first 2% of steps, holds at its peak for the long middle, then decays linearly over the final 15% to a floor of 10% of peak.

def wsd_lr(step, total, peak, warmup_frac=0.02, decay_frac=0.15, min_frac=0.1):
    """Warmup -> stable -> linear decay to `min_frac` x peak."""
    warm = max(1, int(total * warmup_frac))
    decay_start = int(total * (1.0 - decay_frac))
    if step < warm:
        return peak * (step + 1) / warm
    if step < decay_start:
        return peak
    frac = (step - decay_start) / max(1, total - decay_start)
    return peak * (1.0 - (1.0 - min_frac) * min(1.0, frac))

For our run, total = 38,147, so warmup ran for int(38,147 x 0.02) = 762 steps and the first step's learning rate was 6.00e-4 / 762 = 7.87e-7. The run's own step-0 telemetry recorded 7.87e-7, which is a small check that the schedule the loop applied is the schedule written above rather than a different one with the same name.

The reason to prefer WSD is what happens to a checkpoint taken during the stable phase. Its learning rate is the peak, and the peak does not depend on the total step count, so that checkpoint can be branched and trained further under any endpoint you later choose. A run that turns out to be worth extending can be extended. A run that turns out not to be can be decayed early from wherever it has reached, and a decayed model is a usable model rather than an interrupted one.

That property matters here because the constraint on this project was the budget, not the schedule. The whole ladder existed to price a flagship run whose token budget was still being revised, and the token budget was revised, twice. A schedule that had to be declared correctly on step one would have made each revision a restart.

The decay is not merely a cooldown. Loss falls fastest in the decay phase in most WSD runs, and it did in ours: the r1 evaluation series shows held-out perplexity dropping from 15.84 at 4.273B tokens to 13.61 at 5.000B, which is the steepest stretch of the whole run and sits entirely after the decay boundary. The benchmarks chapter takes that curve apart properly.

The anneal and the decay share a boundary

The decay phase is also where the data mix changes. Our corpus was built as two disjoint manifests, 947 stable shards and 94 decay shards, and the decay manifest is weighted toward maths, code and reasoning-heavy text. Both switches are driven by the same predicate:

def in_decay_phase(step, total, decay_frac=0.15):
    return step >= int(total * (1.0 - decay_frac))
want_decay = in_decay_phase(step, total_steps)
if want_decay and phase != "decay" and "decay" in loaders:
    phase = "decay"
    loader = loaders["decay"]
    print(f"[step {step}] entering DECAY phase — switching to the anneal mix")

r1 crossed that boundary at step 32,430, having seen 4.25 billion tokens.1 The predicate flips at int(38,147 x 0.85) = 32,424. The run's history records the transition at 32,430 because telemetry is reported every ten steps after step 1,000, so the first report that saw phase == "decay" was the one at 32,430. The switch happened six steps earlier than the number in the log, which is worth knowing before anyone tries to reconcile the two. From that step onward it trained on the decay mix at a falling learning rate, and the two changes are deliberately not separable in this run. We did not run an ablation with the anneal and the decay at different boundaries, so we cannot attribute the shape of the final loss curve to one rather than the other, and the evaluation chapter says so where it reports the numbers.

The batch, and the number that is not the batch

Four numbers multiply together to make one optimizer step:

sequence length4,096
sequences per microbatch4
microbatch16,384 tokens
gradient accumulation8
tokens per optimizer step131,072

Multiplying that by the 38,147 steps gives 5,000,003,584 tokens, which is where the run's headline token count comes from. It is not a round number because the step count was chosen to reach five billion, not the other way around: round(5e9 / 131,072) = 38,147, and 38,147 steps of 131,072 tokens overshoots five billion by 3,584 tokens.

Now the distinction that the entire next section of this book rests on. Gradient accumulation raises the tokens per optimizer step. It does not raise the microbatch, and the microbatch is what sets MFU.

The GPU never sees 131,072 tokens at once. It sees 16,384 tokens, computes a forward and backward pass on them, keeps the gradients, and does it again seven more times before the optimizer runs. Every kernel launch, every padded expert buffer, every activation tensor is sized by 16,384. Accumulation amortises only the work that happens once per optimizer step — the AdamW update, the gradient clip, the balancer update, the telemetry — and that work is a small fraction of the total.

This is not an argument, it is a measurement, and it was taken on r2, the rung above ours. When the fused situ kernel freed 40 GB, the resulting MFU gain came entirely from being able to raise the microbatch from 16,384 to 24,576 tokens: at equal batch the kernel scored 5.5% against 5.6%, and at the larger microbatch it scored 7.7% at 41,294 tokens per second. The kernel won by allowing a bigger microbatch, not by being faster. Accumulation could not have produced that gain at any setting.2 Which is why the MFU chapters are all about memory. Microbatch is bounded by memory, memory is dominated by activations, and the levers that matter are the ones that make activations smaller. Accumulation is orthogonal to all of it, and it is the first thing people suggest.

For r1 the arithmetic runs as follows. The run sustained 28,936 tokens per second near the end, and MFU is 6 x active_params x tokens_per_second / peak_FLOPs, so 6 x 145e6 x 28,936 / 989e12 = 2.5%. That is the number the loop reported, and it is measured on the real run rather than in a benchmark harness. The same model measured in the harness at a 16,384-token microbatch reached 66,877 tokens per second and 5.9% MFU. Both figures are real; the gap between them is the subject of its own discussion in the opening chapter.

One learning rate, measured once

The peak learning rate came from a single sweep, run at r1's width on short runs: four rates, 600 steps each, on identical data with an identical seed.

lrs = [1e-4, 3e-4, 6e-4, 1e-3]
handles = [run.spawn(which, steps, seq_len, batch, 1, lr, "H200", 0, "",
                     True, None) for lr in lrs]

Short runs are enough for this question because learning-rate problems announce themselves early: too low and the loss plateaus high within a few hundred steps, too high and it spikes or goes to NaN. The sweep recorded zero loss spikes across all four rates, and the best final loss was at 6.00e-4.

Every other rung's learning rate is that one measurement transferred by width:

# r1 hidden  512 -> 6.00e-4      r3 hidden 1024 -> 4.24e-4
# r2 hidden  768 -> 4.90e-4      flagship 1536 -> 3.46e-4
RUNG_LR = {"r1": 6.00e-4, "r2": 4.90e-4, "r3": 4.24e-4}

The rule is 6e-4 * sqrt(512 / width). This is standard-parameterisation transfer, not muP, and it is the weakest assumption in the recipe. Under standard parameterisation the optimal learning rate is expected to fall roughly as the inverse square root of width, which is a rule of thumb with empirical support and not a theorem. muP is the principled alternative: it reparameterises initialisation and per-layer learning rates so that the optimal rate is width-invariant by construction, which would let one sweep transfer exactly instead of approximately. We did not implement it.

Stating this plainly matters more than it might appear, because the flagship's 3.46e-4 was going to be applied to a 35.56-billion-parameter run on two B300s at $7.10 an hour each, derived from one 600-step sweep on a model with a third of the width and a fraction of a percent of the parameters. The flagship failed for an unrelated reason — 69.5% dead experts and a stall at step 890 of 76,294 — so this assumption was never tested at the scale where it would have mattered most.

Weight decay, and a deviation recorded rather than hidden

AdamW ran with betas=(0.9, 0.95), eps=1e-8 and weight decay 0.1, applied through two parameter groups:

def param_groups(model, skip_ids, weight_decay):
    """Two groups: decay the matrices, do not decay anything 1-D."""
    decay, no_decay = [], []
    for p in model.parameters():
        if not p.requires_grad or id(p) in skip_ids:
            continue
        (decay if p.dim() >= 2 else no_decay).append(p)
    return [{"params": decay, "weight_decay": weight_decay},
            {"params": no_decay, "weight_decay": 0.0}]

Everything one-dimensional — RMSNorm gains, biases, KDA's timestep bias — receives no weight decay. Decaying a normalisation gain pulls toward zero the very scale the layer exists to set. Every large open training run does this, so it is a default rather than a tuning choice.

The part worth recording is that the r1 learning-rate sweep that produced 6.00e-4 ran with a single parameter group and decay on everything. The interaction between weight decay on 1-D parameters and the optimal learning rate is second-order, and we did not re-run the sweep after splitting the groups. It is a difference between the conditions the constant was measured under and the conditions it was used under, which is exactly the class of thing that is easy to leave in a code comment nobody reads.

The skip_ids set holds the router's e_score_correction_bias tensors, which are excluded from the optimizer entirely. Their update rule is already fully specified by the balancer, and handing them to AdamW would have momentum and weight decay fighting a rule that is not a gradient. The expert-collapse chapter covers what that rule does.

The spike protocol, written before the run

Loss spikes are a normal event in large pretraining runs and a fatal one if handled badly. The policy was written into the loop before the first real run rather than improvised during it:

  • A step whose loss is NaN or infinite is skipped.
  • A step whose loss exceeds 1.5x a running EMA of recent losses is skipped.
  • A skip means gradients are dropped and the optimizer does not step. One batch of data is lost.
  • Five consecutive skips abort the run and ask for a rollback rather than grinding on through a divergence.

Two details in the implementation are less obvious than the policy.

if self.ema is not None and step > self.warmup_steps and loss > self.ema * self.ratio:
    ...
    return True, f"loss {loss:.3f} > {self.ratio}x EMA {self.ema:.3f}"
# only healthy steps update the baseline, or one spike drags the EMA up
# and the next spike looks normal
self.ema = loss if self.ema is None else 0.98 * self.ema + 0.02 * loss

First, the EMA is updated only on steps that were not skipped. If a spike were folded into the baseline, the baseline would rise toward the spike, and the second spike of a developing divergence would sit under the threshold that the first one broke. The detector would grow more permissive exactly as the run grew less healthy.

Second, the guard's EMA is training state and is saved in the checkpoint. A resume that restarts it at None disables spike detection for the whole of the guard's warmup window and then re-derives a baseline from whatever the loss happens to be at that moment. The run would come back from a crash with its safety system off, at the point in its life when a crash has just demonstrated that something is wrong.3 The checkpoint carries model weights, optimizer moments, the dataloader cursor, all four RNG states, tokens seen, spend to date and the spike-guard EMA. The checkpointing chapter argues that a checkpoint holding anything less is not a checkpoint of the run, and shows the resume-equivalence test that proved this one is.

r1 skipped zero steps across all 38,147. No NaN, no loss above 1.5x its EMA, no aborts. That is a statement about how uneventful the run was rather than about how good the protocol is, and the protocol is untested by it. The place we know the machinery is needed is distributed training, where every rank must reach the same skip decision or the optimizer desynchronises. r1 never met that case: it fit on one H200 and was never sharded, so its guard only ever ran on a single rank. The all-reduce of the loss before the guard sees it was written for the models above r1, and it was on the flagship's two B300s that the desynchronisation it prevents was actually diagnosed. The sharding chapter goes through that bug and the two others alongside it.

The telemetry contract

Every ten steps, rank 0 assembles a dictionary and hands it to the monitor.4 Logging is dense early and sparse later: every step below step 100, every fifth step below step 1,000, then every log_every steps. At 131,072 tokens per step, a flat interval of ten steps puts 1.31 million tokens between reports, which at the run's sustained 28,936 tokens per second is about forty-five seconds of blank dashboard — tolerable in the middle of the run, and far too coarse over the first hundred steps, which is when problems appear. The call is .spawn() rather than .remote(), so a slow monitor cannot throttle training, and the whole thing is wrapped in a bare except that prints and continues. Telemetry observes the run; it must never be able to gate it. The fields are fixed, and choosing them was a design decision rather than an afterthought:

m = {
    "stage": stage, "step": step, "phase": phase,
    "total_steps": total_steps,
    "tokens_seen": tokens_seen,
    "target_tokens": total_steps * step_tokens,
    "loss": loss, "lr": lr, "grad_norm": float(gnorm),
    "mfu": mfu_of(active_params, tok_s, peak_flops),
    "tok_per_s": tok_s,
    "router_entropy_min": router.get("router_entropy_min"),
    "dead_expert_frac": router.get("dead_expert_frac"),
    "load_imbalance": router.get("load_imbalance_max"),
    "spikes_skipped": guard.total_skipped,
    "spend_usd": spend_usd_start + elapsed_h * usd_per_hour,
    "status": "running",
    "eta": f"{(total_steps - step) * dt / 3600:.1f}h",
    ...
}

Three of those fields are worth pointing at.

dead_expert_frac is there because router entropy was not enough. That is the whole subject of the next chapter: at step 20 of the first real run, entropy read 0.99 out of 1.0 while 94.5% of experts were receiving no tokens. Both metrics are reported here, and the gate is on the second one.

tokens_seen against target_tokens is reported rather than derived on the dashboard, because the two can disagree. target_tokens is total_steps x step_tokens, and tokens_seen accumulates what the loader actually delivered, multiplied by the world size on a sharded run. A mismatch between them is a real bug rather than a display quirk.

spend_usd is tracked by the training loop itself, from its own elapsed time and the hourly rate, and it is carried across a resume through the checkpoint. This is what makes a budget gate possible at all: a process that knows what it has spent can be told to stop at a number. An earlier version reset it to zero on resume, which meant an over-budget gate could never fire on a run that had been restarted even once, which is precisely the long run such a gate exists to protect.

The step-0 loss is the one worth checking rather than celebrating. A model that has learned nothing spreads its probability mass evenly over the vocabulary, and the cross-entropy of a uniform distribution over 163,840 tokens is ln(163,840) = 12.007. We measured 12.100. If that number had come out at 6, the loss would have been computed over the wrong axis; if it had come out at 30, the initialisation would have been wrong. It is the cheapest sanity check available in this entire project and it costs one step.

The step-0 throughput of 716 tokens per second against a sustained 28,936 is the allocator growing and the kernels autotuning. This is why MFU measurement discipline in this project always discards the first two steps.

What the loop is for

Almost nothing in this chapter is novel. WSD is standard practice, gradient accumulation is a two-line pattern, spike skipping is folklore that several open runs have published, and no weight decay on 1-D parameters is in every large open recipe.

What made the difference was writing them down before the run rather than during it, and reporting enough state that a failure would be visible from outside the process. The spike protocol never fired. The budget gate never fired. The dead-expert gate never fired. On a run that finishes cleanly, all of that machinery looks like overhead, and the only way to know whether it was worth building is to compare against the flagship, which had the same machinery, collapsed with 69.5% dead experts and load imbalance between 74 and 85, and was stopped at step 890 of 76,294 having spent $48.33. It stopped at 1.2% of its step count, and it stopped because the gates fired.

The loop's job is not to make training work. It is to make the difference between a run that is working and a run that is not visible before the money is gone.
