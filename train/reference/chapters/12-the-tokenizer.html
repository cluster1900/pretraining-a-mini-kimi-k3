The tokenizer we did not train

Chapter 12 of 30 ⏱ 10 min read 📊 5 figures 163,840

Keeping K3's own tiktoken BPE, the byte-for-byte round-trip gate, the literal [EOS] trap that would have injected document breaks mid-page, and why shards are uint32.

Most pretraining projects at this scale train their own tokenizer. It is cheap, it takes an afternoon, and a vocabulary fitted to the corpus gives a smaller embedding table and better compression on the text that matters. For a 1.02-billion-parameter model, a much smaller vocabulary would have been the obvious choice.

We used K3's, unchanged, all 163,840 entries of it. This chapter is about the door that decision keeps open, what it cost in parameters, and the two checks that stand between a tokenizer you believe and a corpus that is quietly wrong.

The reason is a stage that has not happened yet

Reasoning distillation from a large teacher to a small student operates on token distributions. The teacher produces a probability over its vocabulary at each position, the student is trained to match it, and the two vocabularies have to be the same object for that loss to be defined. With a smaller vocabulary of our own there would be no correspondence between the teacher's index 47,203 and anything in the student's table, and the remaining option would be distilling on text rather than on distributions, which discards most of the teacher's signal.

No distillation was performed in this project. r1 is a base model that has only ever done next-token prediction, and we say so wherever the subject comes up. The decision was made anyway, because a vocabulary cannot be revisited later. Changing it invalidates every checkpoint and the whole 104.80-billion-token tokenized corpus.

The bill, in full

A tied embedding costs vocab x hidden parameters and runs on every token in both directions, as the input lookup and as the output projection. At r1's hidden size of 512, that is 163,840 x 512 = 83.9M parameters against a total active count of 145M. The vocabulary is 58% of everything r1 computes per token.

The chapter on scaling down works through what that does to the ladder's design. The comparison worth repeating here is that the same parameter counter, run on K3's released configuration, puts embeddings at 1.1% of K3's active parameters. The same tokenizer, on the model it was built for, is a rounding error; on ours it is the majority of the model.

That is not an argument against the decision; it is the price of it, and it is why the rungs of this ladder are defined on non-embedding active parameters (61M for r1) rather than on the headline figure.

Rebuilding the encoding rather than calling the wrapper

Stage 1 tokenizes on the order of a hundred billion tokens. Moonshot ships a PreTrainedTokenizer subclass, tokenization_kimi.TikTokenTokenizer, which pays Python overhead per document, while the tiktoken.Encoding underneath it releases the GIL and batches across Rust threads. So data/k3_tokenizer.py rebuilds the same Encoding from the same files:

mergeable_ranks = load_tiktoken_bpe(str(d / "tiktoken.model"))
num_base = len(mergeable_ranks)

cfg = json.loads((d / "tokenizer_config.json").read_text())
named = {int(k): v["content"] for k, v in cfg.get("added_tokens_decoder", {}).items()}

special_tokens = {
    named.get(i, f"<|reserved_token_{i}|>"): i
    for i in range(num_base, num_base + NUM_RESERVED_SPECIAL_TOKENS)
}

enc = tiktoken.Encoding(name="tiktoken.model", pat_str=PAT_STR,
                        mergeable_ranks=mergeable_ranks,
                        special_tokens=special_tokens)
if enc.n_vocab != VOCAB_SIZE:
    raise ValueError(f"expected vocab {VOCAB_SIZE}, got {enc.n_vocab}")

The vocabulary is 163,584 base merges plus 256 reserved special ids, which is where 163,840 comes from. [BOS] is 163584 and [EOS] is 163585, the first two of the reserved block.

Rebuilding rather than wrapping means the pre-tokenization regex has to be copied verbatim, including parts of it that do not do what they appear to do.1 PAT_STR contains character-class intersections written in Java syntax, a class of letter and mark categories intersected with && against a negated \p{Han} class. tiktoken's regex engine does not implement && as intersection, so the class does not mean what its author intended. It must still be passed through unchanged, because the released tokenizer was trained and shipped against this literal pattern. A "corrected" pattern would produce a different segmentation and a different model.

Anything rebuilt from parts has to be checked against the thing it replaces, which is what the rest of this chapter is.

The gate

PLAN.md sets one requirement for the tokenizer: the decode round-trip matches. data/verify_tokenizer.py implements that as a short list of checks, ordered by how badly each failure would damage the run.

The first is round-trip equality, decode(encode(x)) == x, byte for byte, across 10 samples covering the ways text differs: English prose, Chinese, code, LaTeX, whitespace, marker text, and one unbroken run of 60,000 non-whitespace characters.

That last sample is a stress probe rather than a piece of text. tiktoken's Rust extension raises a PanicException on very long inputs and on long runs of consecutive non-whitespace characters, and a web crawl and a code corpus both contain exactly that shape: a minified bundle, a base64 blob, a long hash. The shipped wrapper guards against it by splitting a document into encode-safe pieces before handing it to the Rust extension, and k3_tokenizer.py ports the same guard, with the short-document case returning the text unsplit so that the common path allocates nothing.

Without the guard, one pathological document takes down an ingest worker, and a worker that dies halfway leaves a partial shard behind. The check sits in the gate rather than in a comment because the failure appears at ingest time, on real crawled data, where finding out costs hours of CPU.

The remaining checks are quieter. Every id must be below 163,840, so that a uint32 shard is lossless and the embedding table is the size we budgeted. [EOS] must appear exactly once per document and never inside a document body. Bytes per token, aggregated across the content samples, must land inside a plausible range for well-trained BPE; the 60,000-character run is excluded, because letting a synthetic probe move a content statistic would make the check meaningless.2 The exclusion list is one entry long and lives in the source as FERTILITY_EXCLUDE = {"long_run"}. It is a small thing that generalises: a test corpus usually contains both representative samples and adversarial ones, and any statistic computed over the union of the two describes neither.

The last check is agreement with the shipped wrapper, and it is the one worth the rest of the chapter.

The literal [EOS] trap

Our rebuilt encoder must produce the same ids as Moonshot's wrapper, or we are training on a different tokenization than the model was designed for. The check is a straight comparison across the samples, and it passes: all 10 identical, called as hf.encode(t, allow_special_tokens=False). The argument in that call is the interesting part.

TikTokenTokenizer.encode defaults to allow_special_tokens=True. Under that default, a document containing the five characters [EOS] does not tokenize to those characters. It tokenizes to token 163585, the control token our shard format uses to mark where one document ends and the next begins.

For a chat model that is correct: markers in a chat template are supposed to become control tokens. For a pretraining crawl it is a corruption. One web page discussing tokenizer markers is enough for the ingest to write a document separator into the middle of a training sequence. The model then learns that documents sometimes end mid-sentence and resume on the same topic, and every downstream number stays plausible.

encode_ordinary_batch never emits a special token at all, so our encoder cannot produce this failure. We append [EOS] ourselves, once, after each document.

What the gate should then assert took some thought. A test that only checked agreement would fail as soon as we adopted the behaviour a crawl needs, because the two encoders are supposed to differ under the wrapper's default. A test that only checked our own behaviour would not notice if we had drifted away from K3's tokenization. So verify_tokenizer.py asserts both:

# like-for-like: the wrapper called the way we call ours
mismatched = []
for n, t, ids in zip(names, texts, encoded):
    if hf.encode(t, allow_special_tokens=False) != ids[:-1]:
        mismatched.append(n)

# and the divergence we chose, asserted rather than assumed
wrapper_default = hf.encode("[EOS]")
ours = encode_documents(["[EOS]"], num_threads=1)[0][:-1]
if sp["eos"] not in wrapper_default:
    fails.append("wrapper default no longer promotes literal '[EOS]' — "
                 "re-check whether our divergence is still needed")
if sp["eos"] in ours:
    fails.append("our encoder promoted literal '[EOS]' to a control token")

The second half of that is a test that fails when the upstream behaviour changes. If a future release of the wrapper stops promoting marker text, our divergence is no longer needed and the extra code is a liability, and the gate says so rather than continuing to pass silently.3 There is a further trap in the same method, recorded in a comment beside the call. TikTokenTokenizer.encode routes to super().encode the moment any additional keyword argument is passed, and the parent implementation has never heard of allow_special_tokens. The argument is then silently ignored and literal marker text becomes a control token again. The like-for-like comparison therefore passes allow_special_tokens=False and no other kwargs at all, which is a constraint on the call site that no signature communicates.

The shard format, and one byte width that matters

Tokenized output lands at /data/tokens/<source>/<source>-w<worker>-s<seq>.bin as raw little-endian uint32 with no header. Document boundaries are marked by EOS, token 163585, and a .json sidecar carries the token count.

Each of those choices exists for a reason, and the reasons are about what the dataloader has to do when it resumes from a checkpoint deep into a run.

No header means an offset into the file is an offset into the token stream, with no arithmetic. The dataloader's cursor is part of the checkpoint, and restoring it is a seek.

A sidecar rather than a header means the token count can be read without opening the data file, which is what makes the mix planner cheap: mixes.py sizes each source from measured tokens per file across the 1,063 shards by reading only the small JSON files.

EOS as the boundary carries document structure in-band, in the same array as the text, so a shard is a single flat object with no second file that can go out of sync with it.

uint32 rather than uint16 is the choice with teeth. uint16 holds values up to 65,535 and our vocabulary is 163,840, so every id above 65,535 would wrap silently on write, producing a file that opens correctly, has the right length, contains only valid ids, decodes to text and trains without error. No exception, no assertion, no shape mismatch anywhere downstream. The corruption is in the data, and it looks exactly like data.

The cost of that width is recurring. Four bytes per token across a 104.80-billion-token corpus makes storage, not compute, the line item that keeps arriving at $0.09 per GiB per month. The full ingest pass cost about $17 of CPU; the storage has been billed ever since.

The histogram, with thresholds fixed first

The last part of the Stage 1 gate is a token histogram over a sample of the finished shards, reporting three numbers:

statisticmeasuredgated in report.SANITY
vocabulary coverage61.7%a floor
unigram entropy11.74 bitsreported, not gated
most frequent token's share3.54%a ceiling

The most frequent token is a comma.

The floor and the ceiling were written into report.SANITY before any of the numbers existed, which is the only arrangement under which a threshold means anything. A coverage floor chosen after seeing 61.7% describes the result rather than testing it.

Each number checks a specific failure. Coverage asks whether the corpus is as broad as the tokenizer assumes. A frontier multilingual vocabulary applied to a mostly-English corpus will not use all of itself, and 61.7% describes that mismatch fairly. Had it come back very low, the embedding tax would be buying almost nothing.

Top-token share is the check for a stuck separator. If the ingest were writing EOS after every line rather than every document, or if a boilerplate page were repeated across a source, one id would take an implausible fraction of the corpus. At 3.54% for a comma, the distribution has the shape English text has.

Unigram entropy at 11.74 bits is a summary of the distribution rather than a pass/fail gate, and it is worth reading against the loss curve. A uniform distribution over 163,840 tokens carries log2(163,840) = 17.32 bits. The corpus, measured on unigram frequencies with no context at all, carries 11.74. Our run finished at a cross-entropy of 2.623 nats, about 3.78 bits per token. The gap between 11.74 and 3.78 is what 5.00 billion tokens of training bought, and it shows how much of a language model's work is done by context rather than by frequency.

One limitation belongs in the prose rather than only in the code. The histogram is computed over a sample of shards, not the whole corpus, so 61.7% is a sampled figure. Coverage across all 104.80 billion tokens would be a defensible thing to measure and we did not measure it.4 The sampler takes shards at a stride across the sorted shard list and reads a bounded number of tokens from each, which spreads the sample across sources rather than concentrating it in whichever source sorts first. Coverage measured this way can only under-report, since a token appearing in an unsampled shard and nowhere else counts as unused. The reported 61.7% is a lower bound, which is the direction a gate should err in.

What this chapter is really about

The tokenizer decision itself took one line in the plan and produced no numbers beyond the 83.9M-parameter bill. The two checks around it are the part worth carrying elsewhere.

The first is that a deliberate divergence from a library's default has to be asserted rather than merely implemented. Our encoder differs from the shipped wrapper in one respect, that difference is correct for our use and wrong for the wrapper's, and both halves of that statement are now tested. If the upstream default changes, the gate fails.

The second is the shape of the uint16 failure. Most bugs in a pretraining pipeline announce themselves as a shape mismatch, a NaN or a crash. The dangerous ones produce output that passes every structural check and is wrong in its values. We met three in this project: this one, the manifest bug that would have trained the stable phase on 100% finemath, and the router balancer computed on per-rank load rather than global expert load. That third one belongs to the flagship on 2x B300 rather than to our run; r1 trained on one H200 and was never sharded, so it could not have hit it. None of the three would have raised an error. Each was prevented by a check written for it in advance, by someone asking what a silent version of the failure would look like.
